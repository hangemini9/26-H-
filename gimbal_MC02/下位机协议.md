# 与 MC02 的通信 —— Jetson 侧实现说明

对应协议文档 **V3**（`version` 字节 = `0x03`）。这份写 Jetson 侧实现了什么、验证到哪一步、还差什么。

> ⚠️ MC02 build `2026073008` 的二进制解码尚未实现，且协议版本必须**双方同时切到 V3**。
> 版本对不上的现象是"链路有数据但一帧都收不到" —— 收到非 V3 帧时程序会打一次
> `[WARN] 收到 version=0x.. 的帧`，看到这条就是固件版本没跟上。

> **V3 相对 V2 只改了 version 字节**（`0x02` → `0x03`），报文布局一字节没动。
> 改版本号是为了把三条符号约定定死，让新旧固件互相收不到而不是悄悄跑出正反馈：
> ① 球位正方向 = 从中心 O 指向**电机/物理左端**（几何约定，与下坡方向无关）；
> ② `positive_end_px` 填电机/左端像素、`negative_end_px` 填铰链/右端，即使数值大小是反的；
> ③ `command_angle_mdeg` = **物理摆杆倾角**，电机端抬起为正 ⇒ 球加速度为负。
> Jetson 侧过程模型已按 ③ 改成 `ẍ = −ball_accel_gain·α`（见 `main.cpp` 的 `accel_gain`）。

## 0. ★ 题号有两套编号，别搞混 ★

协议内部的 `question_id` **不等于**题面的要求编号：

| `question_id` | 题面第几项 | 测试内容 |
|---:|---:|---|
| 1 | **2** | 跑一圈并停回 A |
| 2 | **3** | 车静止，球 O → +5cm → −5cm |
| 3 | **4** | 从 A 出发通过 B，球保持在 O |
| 4 | **5** | 整圈通过 A，球保持在 O |
| 5 | **6** | 整圈通过 A，球保持在指定位置 |

题面第 1 项（图传/录像/回放）是**公共要求**，不是可选测试项，所以没有对应的 `question_id`。

现场对着题面报分时极容易搞错，所以 `[STAT]` 日志和调试窗都**同时显示两个号**：

```
[STAT ] ... MC02=OK Q3(题面第4项) tx=... 
调试窗:  MC02 OK run=7  Q3=printed#4 [A->B, hold O] state=5
```

## 1. 架构影响（重要）

协议把职责切成：**Jetson 只做"看"，MC02 做"控"**。这推翻了本项目最初的设计。

| | 之前 | 现在 |
|---|---|---|
| 球控制器 | Jetson | **MC02** |
| 目标位置/题目选择 | Jetson `tasks.yaml` | **MC02**（`0x81` 的 `target_position_um`/`question_id`）|
| 角度指令 | Jetson 发 `theta_cmd` | **Jetson 绝不发送** |
| 延迟补偿 | Jetson 外推 | **MC02**（Jetson 只提供 `processing_latency_us`）|

代码上的后果：

- `main.cpp` 里**不存在任何发送角度/使能/CAN 的路径**，`Link` 类也没有暴露这种接口
- Jetson 发的是**取帧时刻的滤波状态**，不做外推 —— 外推该由知道执行器滞后的 MC02 做
- `controller.hpp` 和 `tasks.yaml` **Jetson 已不再使用**，保留下来是给 MC02 固件作者当参考
  （逆动力学 `θ = (1.4·a_des + ax)/g`、初始增益 `kp=25 kd=8 ki=4`、梯形轨迹）
- `control.yaml` 里控制相关的参数移到了 `mc02_reference:` 段，Jetson 只读 `estimator` 和 `plant`

## 3. 还没做 / 需要注意

**① ±125mm 全量程 —— 已经够了（2026-07-30 实测）**

现在的镜头/工作距离实测约 34 px/cm，1440 px 画幅 ≈ 42cm 视野，整根 25cm 管子
连两端支架都在画面里（调试窗的橙框就是管子的实际范围）。所以：

- `calib.valid_range_cm` 保持 ±12.5，全量程可用
- **Q5（题面第 6 项，球保持在任意指定位置）不再受视野限制**，那 20 分能拿
- 早先"6mm 镜头只覆盖 10cm、必须换 2.1mm 广角"的结论已经作废，别再照着改配置
- 超出范围的球仍然会置 `OUT_OF_RANGE` 位并清 `BALL_VALID`（逻辑没变）

**② `CALIBRATED` 位默认不置起**

协议要求中心、端点、符号三者都验证过才能置。现在由 `calib.yaml` 的两个开关控制：

```yaml
fitted: false          # 跑完 tools/calib_fit.py 自动变 true
sign_verified: false   # ★ 做完第一次 STEP +0.5° 实验、确认球往 +x 跑，手动改 true
```

两个都为 true 才置 `CALIBRATED`，MC02 才会闭环。这是故意的——符号错了会直接发散。

**③ `OCCLUDED` 位一直是 0**

classic 后端没有遮挡判据。真需要的话可以拿"边缘对宽度明显小于球径"来判半遮挡。

## 4. 给协议的两条建议

**建议在 `0x81 GIMBAL_STATUS` 里增加两个字段：**

| 字段 | 类型 | 为什么 |
|---|---|---|
| `measured_angle_mdeg` | `int32` | Jetson 侧卡尔曼的过程模型是 `ẍ = 7.0·θ`。现在只有 `command_angle_mdeg`（指令角），连杆回差和电机跟随误差全成了建模误差。另外**倾角视差修正**也需要真实角——相机固定在车体，摆杆一转，球在图像里的位置就会偏，x=+12cm、θ=5° 时可达 1.28cm |
| `chassis_accel_mm_s2` | `int16` | 车纵向加速度。球在车系里受的惯性力等价于重力分量，这一项是过程模型的另一半 |

没有这两个字段，Jetson 的预测精度会下降（现在只能把 `q_accel` 调大到 6.0 硬扛），
`position_um` 的短期外推质量变差，MC02 侧的延迟补偿效果也会打折。
payload 还有余量（24/64 字节），加两个字段不破坏现有布局。

**符号约定已经钉死了（V3，2026-07-30 物理确认）。** 这条建议作废，取而代之的是一条待办：

Jetson 侧还剩**一件**必须现场确认的事 —— 图像的 +x 方向到底指不指向电机/左端。
相机 `flip: "180"` 会把像素方向反过来，所以这个不能靠猜。二十秒的检查：
把球放到**电机那一端**，看调试窗的 `x=` 是不是**正数**。是就把 `calib.sign_verified`
改成 true（`CALIBRATED` 位才会置起、MC02 才会闭环）；不是就把 `calib.p[1]` 取负再复查。
